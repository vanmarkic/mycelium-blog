### Context: What I Was Building

I extended localGPT—a privacy-focused GPT alternative that runs entirely on your machine—with enterprise integrations and knowledge graph capabilities. The work involved three major additions: Watson X integration with IBM Granite models, nano-graphrag for graph-based retrieval, and multi-user authentication with data isolation.

LocalGPT solves a real problem: you want GPT-like capabilities without sending documents to external APIs. Useful for sensitive data, compliance requirements, or offline environments. But the original implementation had gaps: limited model support, no knowledge graphs for complex retrieval, and single-user assumptions.

I added Watson X support (expanding model options beyond Ollama), integrated nano-graphrag (enabling graph-based document retrieval), implemented multi-user authentication (isolating data per user), and expanded file format support (DOCX, HTML, MD, TXT). The goal was making localGPT viable for enterprise use cases while maintaining its privacy-first architecture.

### The Challenge

**Async event loops conflicted everywhere.** Python's asyncio doesn't tolerate multiple event loops in the same process. The nano-graphrag adapter needed async, but localGPT's existing database code also used async. When I integrated both, event loop conflicts crashed the system. The fix required careful async coordination—ensure only one event loop runs, use proper await chains, avoid blocking calls in async contexts.

**Database initialization timing was fragile.** The ChatDatabase needed lazy initialization—don't create database connections until actually needed. But import statements triggered initialization prematurely, causing crashes on startup. I removed direct ChatDatabase imports, added lazy initialization guards, and ensured migrations ran only when databases were accessed, not when modules were imported.

**Multi-user support required rethinking architecture.** The original code assumed single-user: one database, one set of documents, one session. Adding authentication meant: separate databases per user, isolated document storage, migration paths for existing installations. The database migration for existing installations was tricky—detect single-user setups, preserve existing data, create multi-user structure without data loss.

**File format support expanded incrementally.** Adding DOCX and HTML required docling integration. MD and TXT needed custom parsers. Each format had edge cases: malformed HTML, nested DOCX tables, encoding issues in TXT files. Frontend validation needed to match backend capabilities—don't let users upload formats the backend can't process.

**NaN handling broke LanceDB indexing.** Vector databases don't tolerate NaN values in embeddings. But document processing occasionally generated NaN—empty documents, failed embeddings, corrupted text extraction. LanceDB would crash on indexing. I added comprehensive NaN handling: detect NaN in embeddings, filter invalid vectors, log failures, gracefully skip problematic documents.

### How I Solved It

**Watson X integration with OpenAI-compatible API.** IBM's Watson X provides Granite models via an OpenAI-compatible interface. I added environment configuration, raised token limits for larger contexts, exposed Watson X models in the UI. The architecture stayed clean—localGPT's model abstraction layer meant adding Watson X was configuration, not refactoring.

**Nano-graphrag for enhanced retrieval.** Knowledge graphs improve retrieval by understanding relationships between documents. I integrated nano-graphrag with localGPT's existing retrieval pipeline. The adapter used the user-selected model (not hardcoded), leveraged existing embeddings, and added graph-based query expansion. This wasn't a replacement—it augmented vector search with graph reasoning.

**Frontend authentication UI with backend isolation.** I built login/signup UI, added JWT-based sessions, implemented data isolation at the database layer. Each user gets separate document storage, isolated chat history, independent model configurations. Migrations handled existing installations gracefully—detect single-user setup, preserve data, create admin account automatically.

**Lazy database initialization.** Database connections happen on first access, not on import. This prevents premature initialization, allows migrations to run before connections, and makes testing easier. The pattern: check if database exists, run migrations if needed, then connect.

**Comprehensive NaN handling for embeddings.** Before indexing, validate embeddings: check for NaN, filter invalid vectors, log which documents failed. LanceDB only sees clean data. Users see clear errors for documents that couldn't be embedded, not cryptic database crashes.

**File format expansion with validation.** Backend supports DOCX, HTML, MD, TXT via docling and custom parsers. Frontend validation ensures users can only upload supported formats. Error handling catches malformed documents, reports parsing failures, preserves system stability even with corrupted files.

### What I Learned

**Async event loops require discipline in Python.** You can't mix async and sync carelessly. Lazy initialization helps—delay async setup until needed, avoid triggering event loops on import. The nano-graphrag integration taught me to audit every async call for event loop conflicts.

**Database migration paths are first-class features.** Adding multi-user support wasn't just new code—it was migration logic for existing users. The "fix database migration for existing installations" commit proves this: migrations need testing with real legacy data, not just fresh installs.

**Privacy-first architecture constrains integrations.** Watson X integration worked because it uses OpenAI-compatible APIs—no vendor lock-in, runs locally via vLLM if needed. Any integration that requires external API calls breaks localGPT's privacy promise. The constraint is the feature.

**NaN handling is defensive programming.** Vector databases crash on NaN. LLM embeddings occasionally produce NaN (empty input, failed API calls, numerical instability). Comprehensive NaN handling isn't paranoia—it's preventing inevitable production failures.

**Enterprise readiness means multi-user, migrations, and file format support.** The three features—Watson X, multi-user auth, expanded formats—weren't independent. Enterprise users need authentication (multi-user), IBM model support (Watson X), and diverse document types (DOCX, HTML). They're a coherent package.

If I were starting over, I'd design for multi-user from day one. Retrofitting authentication and data isolation is harder than building it upfront. The migration logic worked, but the architecture would be cleaner if multi-tenancy was the default assumption.
