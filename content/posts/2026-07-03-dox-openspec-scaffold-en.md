> A drop-in project-memory scaffold for an Angular 21 / FastAPI repo — two Markdown systems that deliberately never overlap. Some of the OpenSpec command surface below is from mid-2026 docs and may have drifted; I've flagged the parts to confirm against current docs rather than assert them as settled.

A drop-in project-memory setup. Two systems, no overlap:

- **dox** owns *procedural* memory — "how do I work in this area of the code." Hierarchical `AGENTS.md` tree, read top-down before edits, updated after.
- **OpenSpec** owns *decisions and specs* — "what are we building and why." Versioned artifacts in `openspec/`.

Both are plain Markdown in git. Nothing runs, nothing is metered, nothing leaves the machine.

Uncertainty flags: the `AGENTS.md` contents below are hand-authored and safe to use as-is. The **OpenSpec directory layout and command names are from mid-2026 docs and may have drifted** — run `openspec init` and check `openspec --help` for the current surface before relying on exact syntax. The **ADR-schema config format** I am least sure of; treat that section as "confirm against current docs."

## Target layout

```
repo/
├── AGENTS.md                  # dox root: protocol + index + global rules  (auto-loaded by OpenCode)
├── opencode.json              # instructions wiring
├── frontend/
│   └── AGENTS.md              # dox child: Angular 21 local rules
├── backend/
│   └── AGENTS.md              # dox child: FastAPI local rules
├── docs/
│   └── decisions/             # ADRs (MADR format) — the "why" ledger
│       ├── 0000-adr-template.md
│       └── 0001-example.md
└── openspec/                  # generated by `openspec init`
    ├── specs/                 # living source of truth (current state)
    └── changes/               # active proposals (proposal / design / tasks / delta specs)
```

Note on loading: OpenCode auto-loads `AGENTS.md` by traversing **up** from the working directory, so it sees the root by default and a child only when you're already inside that subtree. dox bridges the gap — the root file instructs the agent to walk **down** and read the relevant child before editing. Do **not** glob every `AGENTS.md` into `instructions`; that force-loads the whole tree and defeats the point.

## `AGENTS.md` (root)

```markdown
# Project rules (dox root)

## dox protocol — follow before and after every edit
This project keeps a tree of AGENTS.md files. Each area has local rules.

1. Before editing any file, walk from this root to the target area and READ the
   AGENTS.md files along the path. Do not edit an area blind.
2. Consult docs/decisions/ for any ADR that governs the area you are touching.
3. After a meaningful change, UPDATE the affected AGENTS.md so the docs stay true.
4. If a change alters an architectural decision, do not just edit code — record it
   (see "Decisions" below) or flag that an ADR / OpenSpec change is needed.

## Index
- frontend/AGENTS.md  — Angular 21 app (rules for components, state, tests)
- backend/AGENTS.md   — FastAPI service (rules for routers, DB, auth)
- docs/decisions/     — Architecture Decision Records (the "why")
- openspec/           — specs and in-flight change proposals

## Global conventions
- Language: UK English in prose and comments; Oxford comma.
- Commits: conventional commits. One logical change per commit.
- No secrets in the repo. Config via environment.
- Prefer small, reviewable diffs. If a task spans frontend and backend,
  do the backend contract first, then the frontend against it.

## Decisions vs specs — where things go
- A durable architectural choice (a library, a boundary, a pattern) → an ADR in
  docs/decisions/.
- A feature or behaviour change → an OpenSpec change:
  `openspec propose`, then `openspec apply`, then `openspec archive`.
- A local "how to work here" rule → the nearest AGENTS.md.
Never duplicate the same fact across two of these.
```

## `frontend/AGENTS.md` (Angular 21 child)

```markdown
# Frontend rules (Angular 21)

## Testing — read this before writing or running tests
- Run unit tests via `ng test` (the `@angular/build:unit-test` builder), which
  wires Angular Testing Library + Vitest with correct template resolution.
- Do NOT run `vitest run` directly: it bypasses Angular's build and breaks
  external template/style resolution for components.

## Components
- Standalone components only; no NgModules for new code.
- Signals for local state; prefer `input()` / `output()` over decorators.
- Keep templates in separate .html files; no large inline templates.

## State & data
- Server state through the typed API client; no ad-hoc fetch in components.
- Derive, don't store: computed signals over duplicated state.

## Before editing
- If you touch an API call, confirm the contract against backend/AGENTS.md and
  the relevant OpenSpec spec. Frontend follows the backend contract, never the
  reverse.

## After editing
- Update this file if you introduce a new pattern (a new state approach, a new
  folder convention).
```

## `backend/AGENTS.md` (FastAPI child)

```markdown
# Backend rules (FastAPI)

## Structure
- Routers thin, services hold logic, repositories hold data access. Routers never
  touch the DB directly.
- Pydantic models for all request/response schemas; no raw dicts across a boundary.

## Database
- asyncpg via a connection pool created at startup and closed at shutdown
  (lifespan handler). Never open a connection per request.
- Migrations are the only way schema changes land; no runtime DDL.

## Auth
- Auth is enforced at the router dependency layer. Do not re-implement token
  checks inside services.

## Before editing
- A change to any response schema is a contract change: update the OpenSpec spec
  and notify the frontend (frontend/AGENTS.md) before merging.

## After editing
- Update this file if you add a cross-cutting pattern (new error envelope, new
  pagination convention, etc.).
```

## `opencode.json`

Point `instructions` at genuinely always-on rules only — not the whole dox tree.

```json
{
  "$schema": "https://opencode.ai/config.json",
  "instructions": [
    "openspec/AGENTS.md"
  ]
}
```

`openspec init` writes its own `openspec/AGENTS.md` (or equivalent slash-command guidance) — this line makes those conventions always available. The dox children load on demand via the root protocol, so they are deliberately absent here.

## ADR template — `docs/decisions/0000-adr-template.md`

MADR format. Copy per decision, increment the number.

```markdown
# NNNN. <short decision title>

- Status: proposed | accepted | superseded by ADR-XXXX
- Date: YYYY-MM-DD
- Deciders: <names>

## Context
What problem forced a decision. Constraints, forces at play.

## Options considered
1. <option> — pros / cons
2. <option> — pros / cons

## Decision
The option chosen and the one-line reason it won.

## Consequences
What becomes easier, what becomes harder, what we now owe as follow-up.
```

Example — `docs/decisions/0001-example.md`:

```markdown
# 0001. Use asyncpg with a startup-managed pool

- Status: accepted
- Date: 2026-07-03
- Deciders: Deg

## Context
The API is async and DB-bound. Per-request connections exhaust Postgres under load.

## Options considered
1. SQLAlchemy async ORM — richer, heavier, another abstraction to reason about.
2. asyncpg + a shared pool — thin, fast, explicit SQL.

## Decision
asyncpg with a pool created in the lifespan handler. We want explicit SQL and
minimal layers on the hot path.

## Consequences
Easier: predictable connection use, fast queries.
Harder: no ORM conveniences; migrations and query mapping are hand-rolled.
Owe: a small query-mapping helper to avoid repetition.
```

## OpenSpec setup

Confirm current commands with `openspec --help` after install; names below are from mid-2026 docs.

```bash
# install (per-project or global)
npm install -g @fission-ai/openspec

# scaffold openspec/ and register slash commands for your agent
openspec init

# per change:
#   propose  -> generates proposal / design / tasks / delta specs in changes/<name>/
#   apply    -> implement the tasks
#   archive  -> fold the change's deltas into the living specs/ source of truth
```

The `openspec/specs/` tree is the source of truth for *what the system does now*; `openspec/changes/` holds *what is being changed and why*. On archive, only the spec deltas survive into `specs/`, keeping it current rather than a pile of history.

### ADR schema (optional — least-certain part)

OpenSpec supports custom schemas, and an ADR-alongside-specs variant existed in mid-2026 (configured via the project's OpenSpec config/schema selection). This keeps architectural reasoning inside the OpenSpec lifecycle instead of a separate `docs/decisions/` folder. **Verify the exact enabling syntax against current OpenSpec docs** — I am not confident of the config format. If you enable it, drop `docs/decisions/` to avoid two ADR homes; if you keep decisions in `docs/decisions/`, skip the ADR schema. Do not run both.

## How the pieces interlock (the whole point)

| Question | Where it lives | Read by agent |
|---|---|---|
| "How do I work in this folder?" | nearest `AGENTS.md` (dox) | on demand, top-down before edit |
| "Why did we choose X?" | ADR (`docs/decisions/` or OpenSpec ADR schema) | when touching the affected area |
| "What are we building / changing?" | `openspec/changes/` then `specs/` | during propose / apply |

One fact, one home. dox keeps the how current automatically; OpenSpec and ADRs keep the why and the what durable and reviewable. Total running cost: zero — it is all Markdown your agent already reads and writes as part of normal work.
