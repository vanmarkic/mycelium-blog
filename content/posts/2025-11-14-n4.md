### Context: What I Was Building

I migrated a WordPress investigative journalism site to Kirby CMS, then rebuilt the entire content architecture around an editable block system.

The site—Nationale 4—documents investigative series like "La Tête dans le Béton" (Head in Concrete), exploring infrastructure and environmental concerns. The existing WordPress setup was rigid: custom post types, Elementor blocks, hard-coded layouts. Every content update required wrestling with page builders. Every design change risked breaking existing pages.

I needed a system where editors could compose pages from reusable blocks (interviews, feature cards, donations, resources), where the design system lived in centralized tokens (colors, spacing, typography), and where adding new content types didn't require developer intervention. Kirby's file-based CMS architecture fit this vision—content as structured files, blueprints defining schemas, templates rendering blocks.

The migration had three phases: extract WordPress content to Kirby format, build a flexible block system, then enhance the design with consistent tokens and responsive layouts. The goal wasn't just "same site, different CMS"—it was "better content editing through better architecture."

### The Challenge

**Migration isn't just data conversion—it's content archaeology.** WordPress stores content in MySQL with metadata scattered across multiple tables. Elementor blocks are JSON blobs referencing uploaded media by ID. Extracting this into Kirby's file-based format required parsing exports, reconstructing relationships, and mapping image references from database IDs to local file paths.

The conversion script had to handle multiple content types: episodes (investigative pieces), themes (topic collections), authors, images. Each had different metadata structures. Images were especially tricky—WordPress URLs pointed to a live server, but I needed local file paths organized by episode. I wrote a script to download images and update all references: `promenons-nous-dans-le-béton` had dozens of image tags that needed rewriting.

**Block rendering broke in ways that only appeared in production.** During development, blocks rendered fine. Deploy to test environment? Broken. The issue was blueprint configuration—Kirby's block rendering depends on blueprint definitions matching template expectations. If a blueprint defined a field but the template didn't handle it (or vice versa), silent failures occurred. The test panel showed empty sections where blocks should appear.

**Design consistency required extracting implicit patterns.** The WordPress theme had design values scattered across CSS files—colors defined inline, spacing hardcoded in templates, font sizes copy-pasted. To build a design token system, I had to extract these values, identify duplicates, create a canonical token set, then refactor all components to use tokens. This wasn't just find-and-replace. It required understanding intent: was this `#333333` the primary text color, or a one-off override?

### How I Solved It

**Phase 1: Systematic content extraction**
I built conversion scripts that parsed WordPress XML exports and transformed them into Kirby's folder-based structure. Each episode became a directory with a `default.txt` file containing frontmatter (title, date, author) and content sections. Images got organized into episode-specific folders, with a script updating all references from WordPress URLs to local paths.

The trick was handling edge cases: episodes without images, episodes with broken metadata, episodes referencing deleted media. The script logged every issue, allowing manual review before committing the conversion. Automated where possible, human judgment where necessary.

**Phase 2: Block system with blueprints**
I designed a block architecture with clear separation: blueprints define schemas (what fields a block has), snippets define rendering (how a block displays), templates compose blocks (which blocks appear on a page type).

Key blocks included:
- **Interview block**: Q&A format with speaker attribution
- **Feature card block**: Highlighted content with image and summary
- **Donation block**: Call-to-action for support
- **Content row block**: Flexible text + media layout

The homepage refactor showed this in action. Old version: monolithic template with hardcoded sections. New version: block list rendered dynamically, editors can reorder/add/remove blocks through Kirby's panel without touching code.

**Phase 3: Design token system**
I extracted colors, spacing, typography into CSS custom properties:
- Color variables: `--color-primary`, `--color-text`, `--color-background`
- Spacing scale: `--space-xs` through `--space-xl`
- Typography: `--font-size-base`, `--font-size-heading`, etc.

Then I refactored all components to reference tokens instead of hardcoded values. This created consistency (the same "primary color" everywhere) and flexibility (changing the color scheme meant updating one value, not fifty files).

The REALCO Investigation layout benefited most—enhanced styling using tokens made the entire section visually cohesive without custom CSS per page.

### What I Learned

**Migration scripts are insurance policies.** I could have manually copied content, but one script ran 100x faster and logged every edge case. The time invested in automation paid off immediately when I discovered duplicate entries and broken references the script caught automatically.

**Block systems require upfront design discipline.** Defining blueprints before building templates forced me to think through data structures. What fields does an interview block need? What's required vs optional? This prevented the "just add one more field" sprawl that plagued the WordPress setup.

**Design tokens are refactoring multipliers.** Extracting tokens felt slow initially—finding every color usage, categorizing values, updating references. But once in place, design changes became trivial. Switching from light to dark mode? Update token values. Adjusting spacing for mobile? Change the scale. The upfront cost unlocked long-term velocity.

**Content migration reveals technical debt.** The WordPress export exposed years of accumulated cruft: duplicate images, broken links, inconsistent metadata. Migration created a forcing function to clean this up. Starting fresh in Kirby meant intentionally deciding what to keep and what to discard.

If I were starting over, I'd document the content model before migration. I discovered Kirby's blueprint requirements during conversion, which led to backtracking and rework. A clear schema upfront (episode has: title, date, authors, blocks, images) would have made the conversion script simpler and the blueprint definitions more consistent.
