### Context: What I Was Building

I needed to make localGPT enterprise-ready. Not the fun kind of enterprise where you get to build new features—the hard kind where you retrofit authentication, fix race conditions, and discover that async event loops have opinions about how you structure your code.

LocalGPT is a privacy-focused GPT alternative that runs entirely on your machine. No external APIs, no data leaving your network. Perfect for sensitive documents, compliance requirements, or offline environments. But the original implementation made single-user assumptions: one database, one set of documents, one session. No authentication, limited model support, basic retrieval.

I spent July and October building three major capabilities. Watson X integration with IBM Granite models—expanding beyond Ollama to enterprise-grade options. Nano-graphrag for graph-based document retrieval—augmenting vector search with relationship reasoning. Multi-user authentication with data isolation—separate databases per user, JWT sessions, migration paths for existing installations. Along the way, I expanded file format support (DOCX, HTML, MD, TXT) and fixed the kind of bugs that only surface when real users hit production systems.

### The Challenge

The first time nano-graphrag crashed with an event loop error, I thought I'd made a simple mistake. Import the adapter, wire it up, done. Except Python's asyncio doesn't work that way. You can't have multiple event loops in the same process. Nano-graphrag's adapter used async. LocalGPT's database code used async. When I integrated both, the system imploded with "RuntimeError: This event loop is already running."

I spent a day tracking down every async call. The problem wasn't one function—it was architectural. Async code needs discipline: one event loop, proper await chains, no blocking calls in async contexts. Every integration point needed auditing. This wasn't a bug fix; it was a refactoring forced by Python's runtime.

Then the database initialization started failing. Intermittently. The worst kind of bug. Turns out, the ChatDatabase was initializing on import, not on first use. Import the module, connection opens, migrations try to run, crash because the database directory doesn't exist yet. I needed lazy initialization—defer database connections until actually needed. But that meant tracking down every place that imported ChatDatabase directly and removing those imports. Add initialization guards everywhere. Ensure migrations run only when databases are accessed.

Adding multi-user support revealed how deeply single-user assumptions were baked into the codebase. One database file. One document directory. No concept of user sessions. Authentication required rethinking the architecture: separate SQLite databases per user, isolated document storage, JWT-based sessions. And here's the hard part—migration paths for existing installations. People were already using localGPT in single-user mode. I couldn't just break their setups. Detect single-user installations, preserve existing data, create admin accounts automatically, migrate documents without data loss.

File format support expanded piece by piece. DOCX and HTML needed docling integration. Markdown and plain text needed custom parsers. Each format brought edge cases: malformed HTML that crashed the parser, nested tables in DOCX that broke text extraction, encoding issues in TXT files. And frontend validation had to match backend capabilities exactly—don't let users upload formats you can't handle.

The NaN crash was subtle. LanceDB, the vector database, would fail on indexing with cryptic errors. Took me hours to realize: document processing occasionally generated NaN in embeddings. Empty documents, failed API calls, corrupted text extraction—all produced NaN values. Vector databases don't tolerate NaN. They crash. Hard. I needed comprehensive validation: detect NaN before indexing, filter invalid vectors, log which documents failed, gracefully skip problematic files.

### How I Solved It

Watson X integration turned out easier than expected. IBM's Watson X provides Granite models via an OpenAI-compatible interface, which meant I could reuse localGPT's existing model abstraction. Add environment configuration for API keys and endpoints, raise token limits for larger contexts, expose Watson X models in the UI dropdown. The architecture held up—no refactoring needed. This is why abstraction layers matter: when you design for "any LLM provider," adding a new one becomes configuration instead of code changes.

The nano-graphrag integration was trickier. Knowledge graphs improve retrieval by understanding relationships between documents, not just semantic similarity. I wired nano-graphrag into localGPT's existing retrieval pipeline, but made a key design choice: the adapter uses the user-selected model, not a hardcoded one. This means if someone's running Llama 3 locally, the graph queries use Llama 3. If they're using Watson X, the graph uses Granite. The graph reasoning augments vector search, doesn't replace it. Best of both: semantic similarity plus relationship traversal.

Multi-user authentication required building login/signup UI, adding JWT-based sessions, and implementing data isolation at the database layer. Each user gets a separate SQLite database, isolated document storage, independent model configurations. The migration logic handles existing installations by detecting single-user setups, preserving all existing data, and creating an admin account automatically. No data loss, no manual intervention.

The lazy database initialization pattern became critical. Instead of opening connections on import, defer until first access. Check if database exists, run migrations if needed, then connect. This fixed the intermittent startup crashes and made testing cleaner—test suites can control exactly when databases initialize, not rely on import order.

NaN handling became a validation pipeline. Before indexing any embeddings in LanceDB, check for NaN values. Filter out invalid vectors. Log which documents failed with clear error messages. LanceDB only sees clean data. Users see "Document X couldn't be embedded: empty content" instead of "RuntimeError: NaN values in vector index." Defensive programming, but the right kind—prevent inevitable failures instead of handling them after the fact.

File format support expanded through docling (for DOCX and HTML) and custom parsers (for Markdown and TXT). The key was matching frontend validation to backend capabilities. The upload UI only accepts formats the backend can actually process. Error handling catches malformed documents, reports parsing failures, keeps the system stable even when someone uploads a corrupted DOCX.

### What I Learned

Async event loops in Python demand discipline you don't realize you need until things break. You can't mix async and sync carelessly. The nano-graphrag integration forced me to audit every async call in the codebase. Lazy initialization became a pattern—delay async setup until actually needed, never trigger event loops on import. This isn't just good practice; it's required for async code to coexist peacefully.

Database migrations aren't optional features you add later. They're first-class requirements. Adding multi-user support meant writing migration logic for existing installations, not just supporting new ones. Real users have legacy data, existing databases, configurations that predate your new features. Migrations need testing against actual old setups, not just clean installs. I learned this the hard way when existing installations started failing on upgrade.

Privacy-first architecture isn't just a philosophy—it constrains every integration decision. Watson X integration worked because IBM provides OpenAI-compatible APIs. No vendor lock-in, runs locally via vLLM if needed. But any integration that requires external API calls breaks localGPT's privacy promise. That's not a bug; it's the feature. The constraint shapes the design. If an integration can't run locally, it doesn't belong in localGPT.

NaN handling is defensive programming done right. Vector databases crash on NaN values. LLM embeddings occasionally produce NaN—empty input, failed API calls, numerical instability. I used to think comprehensive validation was paranoid. Now I know it's preventing inevitable production failures. Validate embeddings before indexing. Filter invalid data. Log failures with clear messages. Users appreciate "Document X failed: empty content" more than "RuntimeError: NaN in vector index."

Enterprise readiness isn't one feature—it's a package. Watson X, multi-user auth, expanded file formats. They look independent, but enterprise users need all three. Authentication for multi-tenancy, IBM models for compliance, diverse document types for real workflows. You can't ship one without the others and call it "enterprise ready."

If I were starting over, I'd design for multi-user from day one. Retrofitting authentication and data isolation is harder than building it upfront. The migration logic worked, but the architecture carries scars. Multi-tenancy should be the default assumption, not an afterthought. Single-user mode can be a deployment choice, not an architectural foundation.
