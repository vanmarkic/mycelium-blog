## Introduction

**PAA (Plateforme d'Aide Administrative)** tackles one of civic tech's hardest problems: converting dense legal text into plain language while calculating social benefit eligibility for vulnerable populations.

With **131+ Belgian administrative workflows** encoded, PAA demonstrates a hybrid architecture combining Gherkin specifications, XState state machines, and a rules engine—balancing human readability with executable code and type safety.

## The Story

### Context: What I Was Building

Belgian social benefits are labyrinthine. Eligibility depends on income thresholds, family composition, residency status, disability categories, employment history—variables that interact in non-obvious ways. Legal documents describe these rules in dense paragraphs. Caseworkers interpret them manually. Vulnerable populations often don't know which benefits they qualify for.

PAA addresses two interconnected problems:
1. **Converting legal text to plain language** — making eligibility rules understandable
2. **Automated eligibility calculation** — determining which benefits someone qualifies for based on their situation

The platform uses **Gherkin** for human-readable business rules specification, **XState** for workflow state machines, and **json-rules-engine** for runtime rule evaluation. The result: specifications that both domain experts and computers can understand.

### The Challenge

**Legal logic doesn't map cleanly to code.** Belgian social law has exceptions, special cases, regional variations, and temporal dependencies. A benefit might require "stable residency for 6 months, unless you're a refugee, unless you're applying for specific disability aid, in which case different criteria apply." Traditional if-else chains become unmaintainable.

**Domain experts aren't programmers.** Caseworkers, legal aid workers, and policy analysts understand eligibility rules intimately—but they can't write TypeScript. Gherkin bridges this gap, but naive Gherkin-to-code translation loses nuance. The challenge: maintain executable accuracy while keeping specifications readable.

**131+ workflows with interdependencies.** Some benefits are prerequisites for others. Income thresholds for one program affect eligibility for another. Workflow state needs to propagate correctly—if someone's residency status changes, multiple benefit calculations need updating.

**Multi-language support across FR/NL/DE.** Belgium has three official languages. Benefit eligibility doesn't change, but legal terminology does. The platform must maintain semantic consistency while supporting linguistic variation.

### How I Solved It

**Gherkin specifications as executable documentation.** Business rules live in `.feature` files written in plain language:

```gherkin
Given a person with monthly income below €1,250
And they have resided in Belgium for 6+ months
When they apply for basic income support
Then they are eligible for €950/month
```

These specifications compile to runtime rules via **json-rules-engine**, keeping domain logic auditable and maintainable.

**XState for workflow orchestration.** Benefit applications aren't linear—they have states (submitted, pending verification, approved, appealed). XState state machines model these workflows explicitly, handling transitions, guards, and side effects systematically.

**Type-safety with TypeScript.** While Gherkin provides readability and XState provides orchestration, TypeScript ensures correctness. Workflow states, rule inputs, and calculation outputs are all strongly typed, catching mismatches at compile time.

**Hybrid architecture balancing trade-offs.** Gherkin maximizes readability but lacks type safety. XState provides robust workflow modeling but isn't readable for non-technical users. The rules engine enables runtime flexibility but can't catch logic errors at compile time. The solution: use each where it's strongest, with TypeScript bridging gaps.

**Multi-language support with structured translations.** Legal terms have precise equivalents across FR/NL/DE. The platform maintains translation dictionaries for domain terminology, ensuring semantic consistency while supporting linguistic variation.

**Interactive documentation for 131+ workflows.** Browse all administrative workflows through a searchable, interactive interface. Each workflow shows Gherkin specifications, state diagrams, and example calculations.

**React 18 frontend** with Vite, Radix UI, and Tailwind CSS provides responsive, accessible UI with dark mode support.

**Docker Compose infrastructure** with PostgreSQL and Redis handles data persistence and caching, with pgAdmin and Redis Commander for administration.

### What I Learned

**Executable specifications are a superpower.** When domain experts can read the rules, verify correctness, and the same rules execute in production—you eliminate translation errors. Gherkin isn't perfect, but it's readable enough for collaboration.

**State machines prevent workflow bugs.** Before XState, workflow state was implicit—scattered across boolean flags and status enums. XState makes states explicit and transitions validated. Impossible states become literally impossible.

**Type safety catches semantic errors.** Gherkin-to-rules-engine translation can produce syntactically valid but semantically wrong rules. TypeScript type guards ensure rules receive correct input shapes and produce expected outputs.

**Multi-language legal translation is hard.** Legal terms often lack direct equivalents. What FR calls "revenu d'intégration sociale" and NL calls "leefloon" isn't just translation—they're regionally specific programs with subtle differences. Semantic consistency requires domain expertise, not just dictionaries.

**131 workflows is just the beginning.** Belgium has hundreds more administrative processes. Encoding them all requires tooling for rapid workflow creation, validation, and testing. The proof-of-concept proves feasibility—production requires workflow authoring infrastructure.

If I were starting over, I'd invest earlier in **LLM integration** for conversational assistance. Users shouldn't navigate 131 workflows manually—they should describe their situation in natural language and let AI route them to relevant benefits.
