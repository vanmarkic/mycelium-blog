### Context: What I Was Building

I built an event-centric website for WOMB, an ambient music collective, where the site itself generates atmospheric soundscapes before you even see the content.

WOMB hosts dark ambient events—immersive audio experiences where sound quality and atmosphere matter more than flashy visuals. The website needed to reflect this aesthetic: minimal design, protected audio content (recordings from past events), bilingual support (French/English), and an ambient sound engine that creates evolving soundscapes while visitors browse.

The project evolved through two distinct phases. First, I built a generative ambient sound system using the Web Audio API—randomized frequencies, crackling textures, glitch effects, swipe/touch interactions for mobile. This established the sonic identity. Then I built the full website around it: event archives, artist profiles, protected audio players, gallery lightboxes, newsletter integration.

The technical foundation was Astro for static generation (fast, minimal JavaScript) with Preact components for interactive elements (audio players, galleries, language toggles). Content management through FrontMatter CMS meant non-technical contributors could add events and artists without touching code.

### The Challenge

**Audio format conversion revealed hidden complexity.** I started with WAV files—lossless, high quality, massive file sizes. Browsers struggled. Loading a 50MB WAV over mobile connections meant minutes of waiting. I converted everything to MP3 for bandwidth, but this created a migration challenge: update all event references, ensure audio players handled the new format, verify nothing broke.

The path references were especially tricky. GitHub Pages deployment added `/womb` as a base path, but local development didn't have this. Hardcoded audio paths like `/recordings/episode-1.mp3` worked locally, broke in production. I needed path resolution that worked in both environments. The fix required updating every audio reference AND the base URL configuration AND the audio player component to handle path prefixes correctly.

**Protected audio required blob URL loading.** WOMB recordings aren't public domain—they're exclusive content for event attendees. Direct linking to MP3 files meant anyone could download and share. I needed client-side protection: fetch audio as a blob, create an object URL, pass that to the audio element. This prevents direct hotlinking while still allowing playback in the browser.

But blob URLs complicate caching and preloading. You can't preload a blob URL because the URL doesn't exist until JavaScript runs. This meant balancing protection (blob URLs) with performance (preloading). I chose protection—the audience cares more about exclusivity than milliseconds of load time.

**Ambient sound generation needed controlled randomness.** Truly random audio is chaotic noise. I wanted evolving soundscapes—organic variation within aesthetic boundaries. The sound engine needed randomized parameters (frequency, duration, volume, attack/release envelopes) constrained by musical ranges.

Getting the balance right took iteration. Too much randomness sounded broken. Too little sounded repetitive. I added frequency-dependent volume adjustments (lower frequencies louder, high frequencies subtle), randomized timing between sounds (prevent rhythmic patterns), and multiple sound types (cracks, glitches, crackles, ambient tones). The result felt alive without being distracting.

**Base path issues broke navigation across the site.** Similar to audio paths, internal navigation links failed in production. A link to `/events` worked locally, broke on GitHub Pages (`/womb/events` was needed). Every internal link in every component needed updating. I wrote a verification script to detect broken links before deployment, preventing "works on my machine" disasters.

### How I Solved It

**Phase 1: Generative ambient sound engine**
I built a Web Audio API system that creates evolving soundscapes. The engine:
- Generates randomized tones within frequency ranges (40Hz - 800Hz)
- Applies attack/release envelopes for smooth fades
- Adds crackling/glitch textures for variety
- Adjusts volume based on frequency (bass-heavy aesthetic)
- Responds to keyboard/touch input for manual triggering

The randomization parameters create variation: each page load sounds different, but maintains the dark ambient character. Multitouch and swipe controls on mobile let visitors interact with the soundscape, making the site participatory rather than passive.

**Phase 2: Event-centric content architecture**
I designed content collections for events, artists, recordings, and media. Each collection has a schema defining required fields (title, date, description) and optional fields (images, audio tracks, artist lineup).

The event detail pages became the centerpiece: hero images, markdown descriptions, artist lineup with photos, embedded audio players for recordings. Everything needed to work bilingually, so I built an i18n system with translation files and a language toggle in the header.

The gallery component handles media with a lightbox overlay—click a photo, see it full screen, navigate between images. This required state management in Preact (current image index, lightbox open/closed) and keyboard navigation (arrow keys, escape to close).

**Phase 3: Protected audio player**
The audio player fetches recordings as blobs, creates object URLs, and passes them to the HTML5 audio element. This happens client-side, preventing direct file access. The player includes:
- Play/pause controls
- Progress bar with seek
- Volume adjustment
- Track listing for events with multiple recordings

Event handling improved through iteration—I refactored listeners to prevent memory leaks (remove listeners on component unmount) and handled edge cases (audio fails to load, network errors during playback).

**Phase 4: Content migration and automation**
I built scripts to:
- Convert audio files from WAV to MP3 (ffmpeg)
- Generate image links report (verify all images exist)
- Verify internal links include base path
- Organize media files by episode/event

These scripts automated the tedious parts of content migration, catching errors that manual review would miss.

**Phase 5: FrontMatter CMS integration**
I configured FrontMatter CMS for content editing. This gave non-technical contributors a GUI for:
- Adding new events with metadata
- Uploading artist photos and recordings
- Previewing content before publishing
- Managing translations

The CMS configuration defined content types, field schemas, and preview templates. Contributors edit through a panel, the system generates proper markdown frontmatter and file structure.

### What I Learned

**Audio on the web is still surprisingly hard.** Format support varies across browsers, file sizes matter enormously on mobile, protected playback requires workarounds, and the Web Audio API has sharp edges (garbage collection of audio nodes, buffer size limits, mobile autoplay restrictions). What seems simple—"play an audio file"—becomes complex quickly.

**Base path configuration is a deployment detail that affects everything.** Local development without base paths creates false confidence. Every URL, every path reference, every link assumes context. Deploying to a subdirectory breaks all those assumptions. Testing with base paths in development catches issues early, before they reach production.

**Generative systems require aesthetic constraints.** Random parameters within bounded ranges create variation without chaos. The ambient sound engine works because frequency ranges, volume adjustments, and timing constraints create aesthetic coherence. Pure randomness would be unlistenable.

**Content migration reveals edge cases.** Converting audio formats exposed episodes with missing recordings, broken image references, inconsistent metadata. Migration is archaeology—you discover what actually exists versus what you thought existed. Scripts that verify and report issues are worth the time investment.

**Protection and convenience trade off.** Blob URL loading protects content but complicates caching and preloading. Direct MP3 links perform better but enable copying. I chose protection because the audience values exclusivity, but the performance cost is real. There's no free lunch.

If I were starting over, I'd implement base path handling from the beginning. Retrofitting path resolution across dozens of components and links was tedious and error-prone. A utility function for path resolution (used consistently everywhere) would have saved hours of debugging.
