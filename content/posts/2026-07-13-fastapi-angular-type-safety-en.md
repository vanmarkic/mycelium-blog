> Goal: make it structurally impossible for a type error to reach the browser without something going red — in the editor, in `tsc`, in CI, or at runtime.

## 0. Fix the backend first (highest-yield step)

Everything downstream is generated from the OpenAPI document. If the document is
weak, the generated types are weak, and **TypeScript will be correctly silent
about errors you wanted it to catch**. This is almost certainly what your agent
"missed".

### 0.1 Every endpoint must declare a response model

```python
# BAD — FastAPI emits an empty response schema. Orval generates `unknown`.
@router.get("/items/{item_id}")
async def read_item(item_id: int):
    return await svc.get(item_id)

# GOOD — return type annotation is enough (FastAPI infers response_model)
@router.get("/items/{item_id}")
async def read_item(item_id: int) -> ItemRead:
    return await svc.get(item_id)

# Also GOOD, and required for list/union responses you want narrowed
@router.get("/items", response_model=list[ItemRead])
async def list_items() -> list[ItemRead]: ...
```

Grep for the failure mode:

```bash
# rough heuristic — endpoints with neither a return annotation nor response_model
rg -n '@(router|app)\.(get|post|put|patch|delete)\(' -A 3 app/ \
  | rg -v 'response_model|-> '
```

### 0.2 Declare error responses too

Otherwise your 4xx bodies are untyped and your agent invents error shapes.

```python
@router.get(
    "/items/{item_id}",
    response_model=ItemRead,
    responses={404: {"model": HTTPError}, 422: {"model": HTTPValidationError}},
)
```

### 0.3 Fix the operationIds

FastAPI's default is `read_item_items__item_id__get`, which becomes your Angular
method name. Set this once, before you generate anything, or you will be renaming
your entire client later.

```python
# app/main.py
from fastapi import FastAPI
from fastapi.routing import APIRoute

def custom_generate_unique_id(route: APIRoute) -> str:
    # -> "items-readItem"  (tag prefix keeps names unique across routers)
    tag = route.tags[0] if route.tags else "default"
    return f"{tag}-{route.name}"

app = FastAPI(generate_unique_id_function=custom_generate_unique_id)
```

Then name your handlers deliberately (`read_item`, `create_item`, ...), because
the handler name is now part of your public frontend API.

### 0.4 Export the spec deterministically

Never point Orval at a running server — CI must regenerate without booting the app
and its dependencies.

```python
# scripts/export_openapi.py
import json, sys
from app.main import app

json.dump(app.openapi(), sys.stdout, indent=2, sort_keys=True)
sys.stdout.write("\n")
```

```bash
uv run python scripts/export_openapi.py > openapi.json   # commit this file
```

`sort_keys=True` matters: it makes the file diff-stable, which is what makes the
CI drift gate (§4) work.

## 1. Orval config

```ts
// orval.config.ts
import { defineConfig } from 'orval';

export default defineConfig({
  api: {
    input: {
      target: './openapi.json',   // committed, generated by scripts/export_openapi.py
    },
    output: {
      mode: 'tags-split',         // maps onto FastAPI's tags=[...]
      target: 'src/app/api/generated',
      client: 'angular',
      // Zod-backed models. This is what unlocks runtime validation below.
      schemas: {
        type: 'zod',
        path: 'src/app/api/schemas',
      },
      clean: true,                // NB: wipes the whole output dir, not just its own files
      prettier: true,
      override: {
        angular: {
          // 'httpClient' | 'httpResource' | 'both'
          // 'both' = signal-first reads + imperative writes. Best default for a
          // team migrating incrementally. Requires Angular >= 19.2; stable in v22.
          retrievalClient: 'both',
          // THE important line: pipes every JSON model response through
          // Schema.parse() — .pipe(map(d => Item.parse(d))) for HttpClient,
          // and HttpResourceOptions.parse for httpResource.
          runtimeValidation: true,
        },
        // OpenAPI readOnly fields are response-oriented; strip them from request
        // body types so you aren't forced to send server-owned fields.
        preserveReadonlyRequestBodies: 'strip',
      },
    },
  },
});
```

`zod` must be in `dependencies`, not `devDependencies` — it now ships to the browser.

### What runtime validation does and does not cover

| | Validated at runtime? |
|---|---|
| JSON model responses (GET and mutations) | ✅ automatic |
| JSON `httpResource` retrievals | ✅ automatic |
| Primitives (`string`, `number`, `void`, ...) | ❌ skipped |
| Non-JSON (text, blob, arrayBuffer) | ❌ skipped |
| Custom mutator paths | ⚠️ known gap (orval#2858) |
| **Request bodies** | ❌ **typed, but NOT auto-parsed** |

Request bodies get generated TS types *and* Zod schemas, but Orval does not call
`.parse()` before sending. Do it yourself at the form boundary:

```ts
const payload = CreateItemBody.parse(this.form.getRawValue());
this.itemsService.createItem(payload);
// or .safeParse() if you want to render field-level errors rather than throw
```

### Handling ZodError

```ts
// HttpClient services
this.itemsService.getItem(id).subscribe({
  next: (item) => { /* item is validated */ },
  error: (err) => {
    if (err.name === 'ZodError') {
      // The backend lied. This is a contract bug, not a user error.
      console.error('Response validation failed', err.issues);
    }
  },
});

// httpResource — read err through the error() signal,
// and ALWAYS guard value() with hasValue(): reading value()
// in an error state throws at runtime.
const item = getItemResource(itemId);
const name = computed(() => item.hasValue() ? item.value().name : undefined);
```

Route `ZodError` to Sentry (or whatever you use) with a distinct tag. A ZodError in
production means backend and frontend have diverged — that is exactly the class of
bug you're trying to surface.

## 2. Make TypeScript actually strict

Generated types are worthless if the compiler is lenient. Minimum bar:

```jsonc
// tsconfig.json
{
  "compilerOptions": {
    "strict": true,
    "noImplicitOverride": true,
    "noPropertyAccessFromIndexSignature": true,
    "noUncheckedIndexedAccess": true,     // arr[0] is T | undefined — catches a LOT
    "exactOptionalPropertyTypes": true    // painful for a week, then invaluable
  },
  "angularCompilerOptions": {
    "strictTemplates": true,              // ← templates are where agent errors hide
    "strictInjectionParameters": true,
    "strictInputAccessModifiers": true,
    "typeCheckHostBindings": true
  }
}
```

**`strictTemplates` is the one that matters most for your problem.** Without it,
`.html` files are effectively `any`, and a coding agent writing templates gets zero
compiler feedback. Most "the agent shipped a type error" incidents in Angular live
in templates, not `.ts`.

## 3. Package scripts

```jsonc
// package.json
{
  "scripts": {
    "api:spec":  "cd ../backend && uv run python scripts/export_openapi.py > ../frontend/openapi.json",
    "api:gen":   "orval --config ./orval.config.ts",
    "api:sync":  "npm run api:spec && npm run api:gen",
    "typecheck": "tsc --noEmit -p tsconfig.json && ng build --configuration development --dry-run",
    "check":     "npm run api:sync && npm run typecheck && npm run lint"
  }
}
```

Note: `tsc --noEmit` alone does **not** check Angular templates. Use `ng build`
(or `ng run <project>:extract-i18n`, or the Angular language service in CI) to get
template type checking. This is a common and expensive blind spot.

## 4. CI drift gate

Turns backend/frontend divergence into a red pipeline instead of a production
incident. This is the mechanism that catches what your agent missed.

```yaml
# .github/workflows/api-contract.yml
name: API contract
on: [pull_request]
jobs:
  contract:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
      - uses: actions/setup-node@v4
        with: { node-version: '22.18' }   # Orval 8+ requires Node >= 22.18
      - run: uv sync --directory backend
      - run: npm ci --prefix frontend
      # 1. Regenerate the spec from live Python code
      - run: uv run --directory backend python scripts/export_openapi.py > frontend/openapi.json
      # 2. Regenerate the client from that spec
      - run: npm run api:gen --prefix frontend
      # 3. Fail if anything changed and wasn't committed
      - name: Fail on API drift
        run: |
          git diff --exit-code -- frontend/openapi.json frontend/src/app/api \
            || { echo "::error::API contract drift. Run 'npm run api:sync' and commit."; exit 1; }
      # 4. Full typecheck, including Angular templates
      - run: npm run typecheck --prefix frontend
```

## 5. Tell your coding agent

Put this in `AGENTS.md` / `CLAUDE.md` at the repo root. An agent will not infer
these rules from the code, and this is the cheapest fix available.

```markdown
## API contract — read before touching backend or frontend

The Angular API client in `frontend/src/app/api/**` is GENERATED. Never edit it by
hand; your edits will be wiped by `orval --clean`.

The single source of truth is the FastAPI route definitions. The chain is:

    FastAPI routes → openapi.json → orval → Angular services + Zod schemas

### If you change a FastAPI endpoint (path, params, request body, response model)

You MUST run, from `frontend/`:

    npm run api:sync      # re-export spec + regenerate client
    npm run typecheck     # tsc AND Angular template checking

and commit the resulting `openapi.json` and `src/app/api/**` changes. CI fails
otherwise.

### Every FastAPI endpoint MUST declare its response type

Either a `-> ModelName` return annotation or `response_model=`. Without one,
FastAPI emits an empty schema, orval generates `unknown`, and TypeScript will
silently accept anything. This is the #1 source of undetected type errors here.
Also declare error responses via `responses={404: {"model": HTTPError}}`.

### Do not hand-write TypeScript interfaces for API payloads

Import them from `src/app/api/generated`. If the type you need does not exist,
that means the backend does not declare it — fix the backend, then regenerate.

### Runtime validation is on

Responses are parsed with Zod (`override.angular.runtimeValidation: true`).
A `ZodError` at runtime means the backend response does not match the spec — it is
a contract bug, not a UI bug. Fix the Pydantic model, do not loosen the schema.

Request bodies are NOT auto-validated. Call `CreateItemBody.parse(...)` explicitly
at the form boundary before submitting.
```

## 6. Version constraints (verify against your repo)

| | Requirement |
|---|---|
| Orval | 8+ requires **Node ≥ 22.18** (Docker image available if you're pinned older) |
| `httpResource` | Angular **≥ 19.2** (experimental), **stable in v22** (June 2026) |
| Zod | runtime dependency when `schemas.type: 'zod'` |
| FastAPI / Pydantic v2 | emits **OpenAPI 3.1** |

### The one thing to verify empirically

Pydantic v2 encodes optionality as `anyOf: [{type: X}, {type: "null"}]` rather than
OpenAPI 3.0's `nullable: true`. Orval has been actively patching this class of bug —
recent releases include fixes for nullable composition and OpenAPI 3.1
`$dynamicRef` — but **check the generated types for your `Optional[...]` fields by
hand** before you trust them. This is where I would expect residual sharp edges, and
it is precisely the kind of thing an agent will not flag.
