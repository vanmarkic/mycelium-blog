### Context: What I Was Building

I transformed 3DSoundViz from a proof-of-concept into a production-ready AutoVJ application. The goal was ambitious: create audio visualizations that respond to sound in real-time, with enough flexibility to support multiple physics modes—particles, lava simulations, different rendering approaches.

Early on, I realized the architecture needed to handle three independent concerns: audio processing with configurable sensitivity, physics simulations with different modes, and UI state management. The commit history shows I built these as separate services first, then orchestrated them together. Looking at the progression, I started with the PhysicsService foundations, then added the sensitivity controls, and finally integrated everything into the main app.

The project needed to work on mobile, support multiple color palettes, and deploy automatically via GitHub Actions. Not a weekend prototype—a real application.

### The Challenge

The hardest part wasn't the physics or the GPU rendering. It was making everything **composable** without tight coupling.

The PhysicsService needed to support multiple modes (particles, lava), but I didn't want mode-specific logic scattered throughout. The solution emerged through refactoring: I defined a PhysicsMode interface that made `audioData` optional. This seemed like a small fix at first—just addressing a type error. But it unlocked something bigger: physics modes could now operate independently or react to audio. The interface became the contract.

GPU buffer pooling was another rabbit hole. Memory leaks are insidious in WebGL—you don't notice until the browser tab crashes. I spent time building a buffer pool that recycled GPU resources properly. The fix commits tell the story: "address GPU buffer pool issues" followed by reliability improvements. It took iterations to get right.

Then there was the sensitivity feature. Users needed to adjust how reactive the visualization was to audio. Simple idea, tricky implementation. I needed smoothing (sudden changes look jarring), persistence (save settings), and proper state management (don't enable controls before audio permission is granted). The commits show a classic pattern: build the feature, discover edge cases, fix the edge cases.

### How I Solved It

I built three independent services with clear contracts:

**PhysicsService** orchestrates different visualization modes. Each mode implements the same interface but behaves differently. Particle mode uses GPU rendering with buffer pooling. Lava mode simulates heat diffusion. The service doesn't know or care about the implementation details—it just calls the interface methods.

**AudioService** handles audio input and applies sensitivity scaling. I added smoothing to prevent jarring transitions when users adjust sensitivity. The service maintains state for current sensitivity values and provides an API for UI controls to interact with. Frequency bands get scaled based on user preferences before being passed to physics.

**UIService** manages application state and persistence. This one emerged from a practical need: users were adjusting sensitivity, then refreshing the page and losing their settings. The service loads configuration on init, saves changes to local storage, and manages the state of UI controls (disabled until audio permission is granted).

The integration happened in the main app, where all three services coordinate. Physics modes receive audio data from the AudioService. UI controls update AudioService sensitivity. State changes persist via UIService. Each service focuses on one thing.

GitHub Actions deployment was its own adventure. The Rollup bundler needed native bindings, which GitHub's environment didn't allow by default. I switched to `npm ci` for reliable builds and configured the workflow to allow native bindings. Small fix, but it unblocked automated deployments.

### What I Learned

**Interfaces enable flexibility.** Making `audioData` optional in PhysicsMode wasn't just a type fix—it was a design decision that let physics modes work independently or reactively. The contract mattered more than the implementation.

**State management is never as simple as it seems.** Sensitivity controls taught me that every feature has edge cases: What happens before audio permission? What if settings aren't persisted? What if values change too quickly? Building the UIService forced me to think through these scenarios systematically.

**GPU resource management requires discipline.** Buffer pooling isn't optional for real-time rendering—it's survival. Memory leaks compound quickly in WebGL. The pool pattern works, but you have to commit to it throughout the codebase.

If I were starting over, I'd write the PhysicsMode interface first, before implementing any modes. That contract would have guided the entire architecture. I discovered it through refactoring, but designing it upfront would have saved iterations.
