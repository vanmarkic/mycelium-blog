### Context: What I Was Building

I started building lagendwa on November 5th with a simple goal: create a festival companion app that didn't suck. You know the type—you're at a multi-day music festival with 200+ events, trying to coordinate with friends, remember which artists you liked, and not miss that one experimental noise set at 2 AM in the basement venue.

The initial version came together fast: Astro for static generation, React islands for interactivity, Firebase for real-time sync. I built the basics—favorites, check-ins, a friends feed—thinking I'd be done in a week. Then I tried to build the timeline grid view. That's when things got interesting.

What started as "just show events on a calendar" evolved into a custom sticky-grid system with zoom controls, dynamic column widths, and axes that needed to stay fixed while content scrolled. I ended up extracting the grid logic into its own npm package, migrating to Web Components for framework independence, setting up comprehensive security scanning, and eventually supporting multiple festivals with different data structures. The project became a playground for exploring test-driven development patterns, event sourcing architecture, and the messy reality of building offline-first PWAs.

### The Challenge

The timeline grid nearly broke me. I've built calendars before—how hard could it be? Turns out: very hard when you want time on one axis, venues on another, sticky positioning that works on mobile, and smooth zooming without layout thrashing.

My first attempt used pure CSS Grid with sticky positioning. Looked great in Chrome desktop. Completely fell apart on Mobile Safari. The venue labels wouldn't stay sticky during scroll, the column widths calculated incorrectly, and the time axis would drift out of alignment with the actual events. I spent three days fighting CSS before accepting defeat and rebuilding with a hybrid approach: CSS Grid for layout, JavaScript for synchronization, Web Components for encapsulation.

Then there was the SSR nightmare. Astro builds everything at compile time, which is great for performance but terrible when your grid components try to measure DOM elements that don't exist yet. Service workers that reference `window` during server-side rendering. IndexedDB transactions that abort because the tab lost focus. PWA caching that aggressively served stale versions even after deployment.

The breakthrough came when I stopped fighting the framework and started working with it. SSR compatibility checks wrapped every client-side API. The grid calculations moved to a pure function that could run anywhere. I extracted the sticky positioning logic into its own package with comprehensive tests—which forced me to clarify the contract and revealed edge cases I'd been papering over with "works on my machine" thinking.

What surprised me most: the hardest bugs weren't the grid math or the state management. They were environmental—Firebase env vars with the wrong prefix in CI, Firestore rules that allowed 10-second audio but rejected 30-second recordings, login dropdowns that worked perfectly until the database was empty. The kind of issues you only hit in production, when actual humans use your app in ways you didn't anticipate.

### How I Solved It

I went back to basics: write the test first, make it pass, refactor when you understand the problem better. The timeline grid started as a pure function—`calculateGridLayout(events, venues, startTime, zoomLevel)`—with Vitest tests covering edge cases before a single React component existed. When the layout math worked in isolation, integrating it into the UI was straightforward.

The sticky positioning became its own package (`sticky-grid-axes`) specifically so I could test it independently. I wrote Playwright snapshot tests that scrolled the grid and verified alignment at different zoom levels. This caught the Mobile Safari bug immediately: the axes drifted by 2px per scroll event, compounding until the grid was unusable. The fix required synchronizing scroll events manually, which sounds terrible but made the behavior predictable across browsers.

For SSR compatibility, I wrapped every client-side API in a check: `typeof window !== 'undefined'` before accessing `window`, `IndexedDB`, or `navigator`. Service worker registration moved to a client-only script. The sticky-grid package exported both ESM and CommonJS builds, with explicit handling for server environments. Astro's `client:only` directive became my friend for components that genuinely couldn't render on the server.

The multi-festival architecture emerged from a simple observation: festivals share structure but differ in data sources. I built a registry dispatcher with a strategy pattern—each festival gets its own loader, but they all implement the same contract. Adding Le Guess Who? 2025 after initially building for one festival required zero changes to the grid, favorites, or check-in systems. Just a new strategy in the registry.

Real-time features used Firebase listeners with Nanostores for reactive state. When a friend checks into an event, their activity appears in your feed instantly. The trick was managing subscriptions—listeners that never unsubscribe create memory leaks. I used Svelte's store contract (`subscribe` returns an `unsubscribe` function) so React components could clean up automatically on unmount.

The security posture went from "probably fine" to "provably measured" by integrating OSSF Scorecard, Snyk, and OSV Scanner into CI. Not because I expected vulnerabilities, but because automated scanning surfaces risks before they become incidents. The encrypted CSS payload with domain verification came from wanting IP protection without complex licensing—the app checks it's running on an authorized domain before decrypting the grid styles.

What tied it together: treating tests as documentation. The Playwright specs describe expected behavior in executable form. The Vitest tests show the contract for each utility. The Storybook stories demonstrate the component API. When I onboarded a friend to help with festival data entry, they read the tests to understand how tagging worked—clearer than any README I could've written.

### What I Learned

Test-driven development isn't about tests—it's about feedback loops. The timeline grid worked because I could verify alignment in milliseconds, not minutes. The snapshot tests caught regressions before I deployed. The RED-GREEN-REFACTOR cycle kept me honest when I wanted to hack something together and "fix it later." Later never comes. Write the test now.

Package extraction is underrated as an architectural forcing function. When I pulled `sticky-grid-axes` into its own repo, I had to clarify the contract. What's the API? What's SSR-compatible? What edge cases matter? Questions I'd avoided while the code lived in `src/components/`. Publishing to npm forced me to answer them. The package became better because strangers might use it—even though no stranger ever will.

The hardest bugs live in configuration, not code. I spent hours debugging grid math when the real issue was `VITE_PUBLIC_FIREBASE_API_KEY` versus `PUBLIC_FIREBASE_API_KEY` in GitHub Actions. Firestore rules that worked locally but failed in production. PWA caching that served yesterday's code today. These aren't algorithm problems—they're environmental complexity. Next time: invest in deployment automation early, not late.

Framework independence sounds great until you try to achieve it. I migrated from React to Preact (smaller bundle), back to React (better DX), then to Web Components (framework-agnostic). Each migration cost days. The Web Components version worked but lost the React ecosystem—no Radix UI, no Tailwind integration, no familiar patterns. I ended up back on React with a note to self: pick your dependencies carefully, because switching is expensive.

What would I do differently? Start with the hard problem. I built favorites and check-ins first because they felt achievable. The timeline grid felt scary, so I delayed it. That was backwards. The grid was the core value—everything else was scaffolding. Build the scary thing first. If it doesn't work, you learn early and pivot. If it does work, everything else is downhill.

Most importantly: tests are documentation for future you. Six months from now, I won't remember why the grid synchronization uses `requestAnimationFrame` instead of scroll listeners. But the test will show me: RAF prevents layout thrashing on zoom. The test encodes the reasoning I'd otherwise forget. That's the real value of TDD—not catching bugs, but preserving intent.
